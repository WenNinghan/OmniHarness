# OmniHarness 当前执行、上下文、记忆与权限边界核对

日期：2026-11-08。主体为只读代码与既有验收记录核对，没有进行攻击或新的恢复故障测试。文末补充父任务本轮的真实工具协议测试；不将历史测试当作本轮重跑。

## 总体判断

当前是已经接通持久运行、多模型阶段协作和基础边界控制的 M3 开发预览。还不是能安全读写项目、执行终端、联网搜索的完整通用 Agent，也没有成熟的上下文压缩与长期记忆系统。

最重要的区分：模型支持工具调用协议、框架有受控工具边界，不等于产品已经开放外部工具。现有五阶段中的“执行”是依据输入材料生成结果；“审查”是另一模型的结构化意见，不是实际运行测试。

## 1. 工具调用

- 新 Run 默认五阶段图 `stage-agent-v2`。`src/omniharness/m3_stages.py:151` 明确构造无外部工具的图，`:204` 拒绝返回 tool_calls 的响应；`stage_contract.py:11-19` 明确没有文件、命令、网络与验证工具。
- 旧版 Deep Agents 图仍保留。`m3_worker.py:71-79` 构造每个角色时传 `tools=()`，`:428-435` 接入受控构造器与两级委派调度器。
- `m3_agents.py:269-305` 检查 `task` 委派目标及角色工具白名单，未授权工具拒绝执行；`:308-317` 只接受显式、可信 `BaseTool`。因此 SDK 内置的文件工具不会仅因 SDK 存在就获得权限。对应现有回归用例：`tests/test_m3_agents.py:339` 拒绝未授权内置文件工具，`:379` 预算拒绝后不执行 handler。
- 新图最多 8 个计划步骤、8 个执行任务，依赖关系受结构校验；`m3_stages.py:271-281` 每批最多两个依赖已满足的任务。
- `plugins.py:12-45` 有 Tool、Verifier、Provider、Workflow、Search 的契约与 permissions/side_effect 声明，`:60-72` 有入口点发现与 API 版本检查。但这不构成已开放的产品工具网关；插件被作为可信 Python 加载。

缺失：工作区注册与挂载探测、真实文件/补丁/终端工具、Sandbox Controller、MCP 客户端接线、搜索/抓取工具、运行真实测试的 Verifier、绑定操作参数和工件版本的审批流程。

依据补充：在 `src/omniharness/api.py` 与 `models.py` 搜索 `approval|sandbox|memory|mcp|workspace` 没有对应端点/实体命中；搜索整个后端仅发现插件声明和边界说明。`docs/M3-stage-models.md:24-26` 明确这些仍属于 M4/M5。

## 2. 上下文管理

- 同一会话的历史从数据库按 Run 顺序读入，未从其他会话自动召回。`worker.py:296-302`、`m3_worker.py:394-400`。
- 只有用户输入和完整回答进入后续历史，截断/失败回答不作为完整上下文；`services.py:180-185`。
- 默认 100 条消息、200000 字符，来自 `settings.py:26-27`。普通聊天对历史字符检查；Agent 在每次实际调用前额外检查序列化消息、system 与结构化内容：`m3_agents.py:98-117`、`m3_stages.py:165-172`。这些是字符上限，不是 token 精确计算，也没有按不同模型的窗口动态适配。
- 超限明确失败或在并发结果不确定时进入待核对，不静默丢弃历史。`m3_worker.py:155-165`。
- Deep Agents 自动摘要被 `NoImplicitSummarization` 明确替换，原因是 SDK 摘要可产生绕过当前模型调用预算钩子的请求；`m3_agents.py:162-171,363,385,391`。不是已经完成了宿主摘要器。
- 阶段之间交付正式输出；`m3_stages.py:177-182` 不把其他模型的私有 reasoning/signature 作为跨阶段内容继续发送。

缺失：模型窗口登记、按 token 计数、输入预算与输出预留、滚动摘要、旧消息压缩、超长工具结果落盘及引用召回、每阶段精准挑选上下文。

本轮 100K 是最大输出 token 配置，和输入上下文是两个维度。它不会放大 100 条/20 万字符限制，长结果被下一阶段纳入消息后仍可能触发上下文停止。

## 3. 记忆

已有两类持久数据：会话消息、Run/事件/阶段产物；以及用于暂停与恢复的 PostgreSQL LangGraph 检查点。`models.py` 的 Message/Run/RunEvent 与 `m3_worker.py:410-473`。

这能够保留聊天与运行进度、浏览器刷新或进程重启后的记录；不代表自动记住用户偏好、项目知识或跨会话经验。后端搜索 `memory|memor|vector|retriev|embedding|长期记忆` 未发现长期记忆存储/检索实现；摘要相关命中是禁用摘要或回答字段。

缺失：显式项目记忆、用户可查看/纠正/删除的长期事实、来源与有效期、任务结果提炼、检索召回与冲突处理、避免把模型猜测固化为事实的写入策略。

## 4. 约束与恢复风控

- 默认模型调用 50、工具调用 100、修订预算字段 2、活跃时间 1800 秒；`settings.py:28-31`。预算在 Run 创建时冻结，主子代理共享；`services.py:472-500`、`m3_budget.py:31-78`。
- 调用先按 invocation_id/参数绑定预留额度；重复身份、不同输入或不明结果不等于获得重复执行许可。`m3_host.py:172-245`、`m3_budget.py:1-5`。
- 暂停/继续/补充要求走持久命令，调用边界检查；`m3_host.py:122-145`。取消是尽力中断，不能撤回已经发到供应商的请求。
- Worker 使用 PostgreSQL 会话锁，持有该连接做所有权事务；`worker.py:33-110`。检查点另外做线程/所有者 fencing；`checkpoint_fencing.py`。旧 Worker 失锁后不能继续合法写结果。
- 结果不明、活跃时间不明等情况进入 pending_review，不自动重放；`m3_worker.py:114-165,439-458`。SDK 显式 `max_retries=0`：`providers.py:177,191,202`。
- 旧 Deep Agents 委派最多两级、两个活跃子代理；`m3_delegation.py:102,195-197`；新图按依赖批次最多两个执行任务。

缺失/须准确表述：

- 目前没有以人民币/美元为硬约束的 Run 费用额度，也没有跨调用总 token 硬预算；次数与时间限制不能等价为精确成本限制。
- 修订预算字段不代表已实现审查失败后的真实修复闭环。新图 `m3_stages.py:328-340` 从审查到 finish，没有修订循环。
- pending_review 是恢复不确定状态，不是高风险操作批准接口。

## 5. 权限与秘密边界

- 单机服务：Compose 只向宿主 `127.0.0.1` 映射 8787，PostgreSQL 不映射宿主端口；`compose.yaml:28-44,66-71`。
- 首次配对码 15 分钟、一次性消费；本地会话 token 哈希保存。`security.py:48-79`。API 配对限流、HttpOnly/SameSite=strict Cookie；`api.py:173-188`。
- 接口认证、来源检查、变更请求头、Host 检查及 CSP；`api.py:108-136,154-158`。这是本地单用户模型，不是多用户角色权限系统。
- Provider Key 用 Fernet 加密，主密钥在独立秘密目录；`security.py:16-42`。配置导出排除 api_key；`api.py:237-243`。异常不回显原始请求、响应或认证头：`providers.py:69-91`。
- 模型调用关闭 LangSmith tracing；`m3_worker.py:471`、`providers.py:252,381`。模型 Key 由宿主提供，阶段提示不传入 Key。
- 当前 API/Worker 容器非 root、cap_drop ALL、no-new-privileges，秘密目录只读挂载；`compose.yaml:21-26,78-80,96-105`。这些是服务容器约束，不是已经完成了工具执行沙箱。
- 用户配置的模型 endpoint 可使用 HTTP(S) 并可指向本地模型，拒绝 URL 内凭据/查询/片段；`providers.py:103-119`。没有按项目配置的出网白名单，也不是一套不可信代码网络隔离机制。

限制：Python 插件是可信进程内代码，有权限声明但无恶意插件隔离；数据库访问权限相同的恶意插件不受检查点 fencing 保护（`checkpoint_fencing.py:1-5`）。消息/检查点是持久数据，并非所有内容都做加密或脱敏；普通会话内容会按所选模型发给对应供应商。当前还没有文档/网页指令污染与长期记忆写入的完整治理流程。

## 6. 验证证据的边界

既有报告 `docs/M3-preview.md` 记录了真实 DeepSeek 三次模型调用/一次委派冒烟，以及专用 PostgreSQL 恢复/失锁/上下文测试；`docs/M3-stage-models.md:19` 记录两种真实模型完成五阶段结构化链路。它们证明这些单次调用和对应测试场景，不证明质量提升、完整工具能力、所有 Provider 兼容性或恶意插件隔离。

只读核对阶段仅查看上述代码与测试，未重跑安全/恢复故障矩阵；本轮真实工具协议与部署补充验收见第8节。

## 7. 建议优先级

1. 落实 M4 的最小真实工具闭环：登记项目 → 受控读取/补丁 → 独立沙箱命令 → 真实测试输出；把工作区范围、网络策略、操作参数审批和结果不明处理一起接入。
2. 同步做按模型 token 窗口的上下文预算与受预算约束的摘要；长工具输出转工件引用，保护用户要求、当前计划和验证证据。
3. 先做可查看、可编辑、带来源的项目记忆，再按真实召回需求决定向量检索；避免直接把全部聊天“自动记住”。
4. 增加真正的费用预算/预留与结算边界，价格未知时保留未知，不把参考倍率当实扣账单。

这些是下一步建议，不是本轮已授权的新增实现范围。
